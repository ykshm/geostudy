# 章別地図の作りかた(site/MAPS.md)

本書は、章のウェブ版に付く地図(地図パネルと章末おまけ)を作る作業の指示書である。読み手は、この作業を担当するClaudeのセッション——あなた——である。

## 0. 位置づけ(最初に読むこと)

- 地図は**ウェブ版限定の機能**であり、**執筆とは別の後工程**である。紙面(本文・注釈・図版)には一切関与しない。**正本のMarkdown(text/)には決して手を入れない**(正本不可侵。site/README.md参照)。
- 地図がなくても章は完成である。地図は完成した章に、後から付ける。
- 地図の文章(地名の一行説明、スナップの実況文)は**裏方の声**で書く。章の著者の声ではないし、著者を演じてもいけない。紙面の三者構造(CONCEPT.md 2節)の外にある、道具の説明文である。調子は観察的な実況——説明ではなく、隣を歩いている人のつぶやき。

## 1. 仕組み

- 章ごとのデータは `site/geo/<シリーズ>/<slug>.json` に置く(例: usa の章は `site/geo/usa/tx.json`)。**作るのはこのJSONファイル(と検証記録)だけ**である。
- `site/build.py` がビルド時に、テンプレート(`site/maps/template.html`)にJSONを埋め込んで `_site/maps/<シリーズ>-<slug>.html` を生成し、章ページに①本文の地名の📍リンク、②右下ボタンの地図パネル、③章末「おまけ: 地図で歩き直す」節を自動で付ける。
- JSONの書式が壊れているとビルドが失敗する(lintを兼ねる)。地図の見た目や動きを変えたいときはテンプレートを直す——全章に一度で効く。生成物(_site/)は直接編集しない。
- 層は三つ——places(本文の地名)、snaps(暮らしのスナップ)、extras(補遺の見どころ。text/japan/series.md 11節)。extras は臥遊風土記では標準、アメリカ50州では任意(無ければ✦のピンもチップも出ない)。

## 2. geo/<シリーズ>/<slug>.json の書きかた

`site/geo/usa/tx.json` が見本である。構造:

- `map`: 出力先。`"maps/<シリーズ>-<slug>.html"` に固定。
- `title`: 地図ページの題。「<章題> — 章の地名地図」。
- `places`: 本文の筋の地名(8〜12個目安、本文の登場順)。各項目:
  - `i`: 通し番号(0始まり。本文リンクの data-i に対応)
  - `name`: 地名(本文中の表記と**一字一句同じ**にする。リンク化は文字列一致で行われる)
  - `sec` または `note`: リンクを付ける場所。節番号(例 `"3"`)か注番号(例 `"12"`)の**どちらか一方**。その節/注での初出1回だけがリンク化される
  - `side`: 省略可。米国外の地名は `"mx"` 等(ピンとチップの色が変わる)
  - `lat` / `lng`: 座標(小数4桁で十分)
  - `text`: 一行の説明(本文モードでも見える)
  - `rich` / `img` / `credit`: おまけモード用。写真の一言・写真URL・帰属表示
- `snaps`: 暮らしのスナップ(5〜8枚)。各項目: `name` / `lat` / `lng` / `era` / `text` / `img` / `credit`。
- `extras`: 補遺の見どころ(3〜5個目安)。各項目: `name` / `lat` / `lng` / `text` / `img` / `credit`(eraは無し)。おまけモード限定で✦のピンとチップになる。

## 3. 地名(places)の選びかた

1. 章を通読し、**本文の筋を運んでいる地名**を選ぶ。網羅ではない——読者が「どこの話だろう」と地図を見たくなる地名だけ。
2. 各地名の登場箇所(節/注)を確かめ、`sec`/`note` を指定する。冒頭のプロフィール表と目次はリンク対象外。本文に出ず図の説明文にだけ出る地名も、その節を指定すればリンク化される。
3. 座標は市街中心か、章が語る当の場所(丘・ダム等はその地点)。
4. `text` は「その地名が章の中で担っている役割」を一行で。

## 4. 写真の選びかた(2種類で基準が違う)

**places の写真(おまけモードで表示)** — その土地の代表的な一枚でよい。街ならスカイライン、場所ならその場所自体。

**snaps(暮らしのスナップ)** — 選定の哲学が違う。
- **写真ファースト**: 地名から写真を探すのではなく、まず「場面の良い写真」を見つけ、良いものがあった場所にピンを置く。凡庸な写真で数を揃えない。
- **観光地でない、ふだんの生活の場面**: 田舎町のファストフード店、下町の食堂の通り、生活道路、地元の行事。絵はがきにならない風景ほど良い。人は写っていてもいなくてもよい——場面の良さが全て。ただし現代の私人の顔が大写しの写真は避ける。
- **現代中心+昔を1〜2枚**: 昔の日常写真の宝庫は連邦のコレクション(1970年代のDOCUMERICA、1930-40年代のFSA/OWI——いずれもパブリックドメイン)。混ぜるときは `era` に年代を明記する(例 `"1972年"`。現代は `"いま"`)。
- **実況文(text)**: 観察的な1〜2文。写真の中の時間を語る(例:「金曜の夜は、町中がスタジアムへ行く」)。事典的説明にしない。

**extras(補遺の見どころ)** — snapsともplacesとも基準が違う(text/japan/series.md 11節)。
- 著者が紙面で拾わなかった見どころを、裏方の**別の目**で拾う。著者の偏愛を補う視線であって、著者の代弁ではない。
- **定番より意外性**。ガイドブックの一位は要らない。章の筋と響き合うものはなお良い。
- 文は裏方の声で一行(1〜2文)。実用情報(営業時間・料金・行き方)は書かない。
- 著者がすでに注などで推した見どころと重複させない。

## 5. 写真の権利と技術要件(必須)

- 使えるのはパブリックドメインか再配布可のCCライセンスのみ。**採用前にCommonsのファイルページでライセンスを確認**する(APIの extmetadata が楽)。CC BY / CC BY-SA は `credit` に作者名とライセンス名を必ず書く(表示はライセンスの要件)。PDは「パブリックドメイン」と書く。
- `img` は upload.wikimedia.org の**500pxサムネイルのURL**(Commonsに置いたまま直リンクする。リポジトリには置かない)。タップ拡大は自動で1280px版に差し替わるため、**原画像の幅が1280px以上**のものを選ぶ。
- .tif の原画像はサムネイルのパスが `lossy-page1-500px-〜.tif.jpg` の形になる(APIの thumburl をそのまま使えば間違いない)。
- 全URLがHTTP 200を返すことを確認する。

## 6. 検証と納品

1. `python site/build.py` が警告・エラーなしで通ること(JSONの書式検査を兼ねる)。
2. `_site/` をHTTPサーバで開き、ブラウザで確認する(`file://` では動きが変わる):
   - [ ] 地図パネルが開閉し、本文の📍地名タップで該当地点に飛んで吹き出しが開く
   - [ ] チップで全地名を順に回れる。ピンの節番号表示が正しい
   - [ ] `?rich` で写真・クレジット・📷スナップピンが出る。写真タップで全画面拡大が動く
   - [ ] モバイル幅でも上記が動く
   - [ ] 他の章のページに影響がない
3. 検証記録を `site/geo/<シリーズ>/<slug>-check.md` に残す(採用した各写真のCommonsファイル名・作者・ライセンス・確認日、座標や実況文の根拠で特記があれば)。`site/geo/usa/tx-check.md` が見本。
4. コミット・push・PR。マージでPagesに反映される。

## 7. やらないこと

- 正本のMarkdownを変えること(地名の表記が地図の都合で不便でも、直すのは紙面ではなくJSON側)。
- ストリートビュー等の外部サービスへのリンクを足すこと(過去に入れて、依頼者の判断で外した経緯がある)。
- ライセンスの怪しい写真を妥協して使うこと。良い写真がなければ、その場所のスナップは置かない。
